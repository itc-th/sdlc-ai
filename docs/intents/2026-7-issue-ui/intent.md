## ปัญหาและที่มา
ระบบมี DB schema และ authentication แล้ว แต่ยังไม่มีหน้าจอให้ผู้ใช้จัดการ issue ตามกระบวนการใน docs/process.md ขั้น 1-2 (รับเรื่อง คัดแยก) ต้องทำผ่าน DB โดยตรง

## ทำไมต้องทำ
ถ้าไม่มีหน้าจอ ทีมไม่สามารถรับเรื่อง คัดแยก หรือติดตามสถานะ issue ผ่านเว็บได้ เป็นฟีเจอร์พื้นฐานที่ทุก role ต้องใช้

## ผู้ใช้ที่เกี่ยวข้อง
- Helpdesk — สร้าง issue ใหม่ (~5-10 คน)
- SA — ดูรายการ คัดแยก มอบหมาย (~3-5 คน)
- Programmer, Tech Lead — ดูรายการ issue ที่ได้รับมอบหมาย
- ผู้บริหาร — ดูภาพรวม issue

## ขอบเขต
- ทำ:
  - หน้ารายการ issue พร้อมกรอง status/type/risk
  - หน้ารายละเอียด issue
  - ฟอร์มสร้าง issue ใหม่
  - ฟังก์ชันคัดแยก (triage) สำหรับ SA
  - API endpoints พร้อมตรวจ session
  - บันทึก audit log เมื่อสร้าง/อัปเดต issue
- ไม่ทำ:
  - ยังไม่เชื่อม GitHub sync (จะทำในงานถัดไป)
  - ยังไม่ทำ intent/spec management ในหน้าเว็บ
  - ยังไม่ทำ role-based access control ละเอียด (ทุก role เห็นทุก issue)
  - ยังไม่ทำ pagination (จะเพิ่มเมื่อข้อมูลเยอะ)

## เกณฑ์ว่าเสร็จ
- [ ] หน้ารายการ issue แสดงข้อมูลจาก DB ได้
- [ ] กรอง issue ตาม status, type, risk ได้
- [ ] สร้าง issue ใหม่ผ่านฟอร์มและบันทึกลง DB ได้
- [ ] SA คัดแยก issue (เปลี่ยน type, risk, status, assignee) ได้
- [ ] API ตรวจสิทธิ์ที่ฝั่ง server ทุกเส้น
- [ ] บันทึก audit log เมื่อสร้าง/อัปเดต issue
- [ ] `pnpm build` ผ่านทุก package
- [ ] `pnpm lint` ผ่านทุก package

## ระบบและข้อมูลที่แตะ
- โฟลเดอร์: `apps/web` (หน้าจอ, API routes)
- ฐานข้อมูล: อ่าน/เขียนตาราง issues, users, audit_logs, projects
- ไม่แตะ packages/db schema (ใช้ schema ที่มีอยู่)

## ความเสี่ยง
- [ ] ข้อมูลส่วนบุคคล
- [ ] สิทธิ์ผู้ใช้ / การยืนยันตัวตน — ตรวจ session ทุก API
- [ ] โครงสร้างฐานข้อมูล
- [ ] ข้อมูลงบประมาณ

ระดับ: กลาง (แตะ API ที่ระบบอื่นอาจเรียกใช้ในอนาคต)
ผู้อนุมัติเพิ่มเติม: SA, เจ้าของ policy

## ข้อจำกัด
- ต้องตรวจและจำกัดข้อมูลนำเข้าทุกจุด (validation)
- การกระทำสำคัญต้องบันทึกใน audit log
- ข้อมูลนำเข้าต้องไม่มี XSS
